# Malloyyo 0.2.31

_2026-08-19 · everything since 0.2.19 (2026-07-27)_

Three weeks, 32 commits, twelve releases, and one theme —
**a Malloyyo dashboard no longer needs Malloyyo running.**

0.2.19 made dashboards load well inside the hosted app. This batch takes them
out of it: `malloyyo dashboard bundle` compiles a model repo into a directory
of static files that GitHub Pages serves straight from the branch, with Malloy
compiling in the browser, DuckDB-WASM running the SQL, and the data sitting in
the repo next to it. No server, no token, no database, no CORS policy.

Around that: analytics configured once in `malloy-config.json` instead of
remembered per rebuild, a published container image for hosted instances,
`malloyyo sql`, shareable URLs for custom components, and a run of fixes whose
common shape is *the thing that broke told you the wrong thing.*

---

## Dashboards as a static site

```bash
malloyyo dashboard bundle --out docs
malloyyo dashboard bundle --target vercel --duckdb bundled
```

The bundler is a fourth host behind the existing `host.run` seam, alongside the
sandboxed iframe (postMessage), the in-page shell (fetch `/api/run`), and the
hosted app. With no credential in the page there's no trust boundary to sandbox
across, so custom and tag-only dashboards share one in-page mount.

- **Everything that can move to build time does.** Model sources are inlined,
  given specs are introspected once, components are precompiled, and esbuild
  code-splitting puts Malloy/DuckDB/Vega in one shared chunk the browser caches
  across dashboards.
- **Targets differ only in host adapter, not artifact.** `pages` emits
  `.nojekyll` and `.html` URLs (no headers possible, single-threaded);
  `vercel` emits a `vercel.json` with clean URLs and immutable asset caching.
- **DuckDB comes from jsDelivr** at the exact installed version — immutable,
  CORS-open, brotli, ~6.8 MB vs 7.7 MB gzipped self-hosted — which keeps 75 MB
  of binaries out of the repo. `--duckdb bundled` self-hosts for an offline or
  fully self-contained deploy.
- **Three things got shared rather than duplicated**, because the copies had
  already drifted: `shared/givens-url` (the static copy stripped the `$` prefix
  the runtime keys off, so every shareable link fell back to defaults),
  `shared/nav`, and `discover.ts` — so the bundler no longer imports the dev
  *server* just to find dashboards.

## Your data lives in the repo — no object store, no CORS

A model can reference data by a path relative to the project root:

```malloy
duckdb.table('docs/imdb_titles.parquet')
```

and that one spelling works in VSCode, in `dashboard dev` (DuckDB reads the file
off disk), and in the published site. The build maps each reference to the href
the page fetches and registers the bytes under the model's *original* name, so
the model text never changes per host.

The href is always the file's path relative to the site root, which covers both
layouts — `data/x.parquet --out docs` becomes `./data/x.parquet` (copied in),
and `docs/x.parquet --out docs` becomes `./x.parquet` (already there). The
second is worth preferring when `docs/` is committed for Pages: the data lives
in git once instead of twice. Either way the fetch is same-origin, so a
self-hosted dataset needs **no CORS configuration at all** — which deleted the
two most error-prone steps of publishing, and `gcloud` from the prerequisites.

Two sharp edges handled along the way: table references are collected only from
model files *reachable by following imports from the dashboards* (a stray
`gs.malloy` next to the one actually imported was making the page download a
second full copy of its data), and the build records what it copied and removes
a previous run's orphans (moving data from `data/` to `docs/` otherwise left
12 MB behind, straight into a commit).

There's a full runbook in
[publishing-to-github-pages.md](../publishing-to-github-pages.md) — from an
empty directory to a live site, written so an agent can execute it, with a
verification gate on every step because the failure modes are mostly silent: a
404'd wasm asset hangs with no console error, and a model reading a table the
browser can't fetch builds green and breaks only in the published site.

## Analytics from config, on bundled sites and hosted instances alike

`--analytics G-XXXXXXXXXX` shipped first and was the wrong shape: a Measurement
ID is a property of the project, not of one invocation, so a flag means every
rebuild has to remember it — which already went wrong once. It's config now:

```json
{ "malloyyo": {
    "analytics": "G-XXXXXXXXXX",
    "targets": { "prod": { "url": "…", "dataset": "…" } }
} }
```

Hosted instances take the same setting as an `ANALYTICS_ID` environment
variable, rendered from the root layout, so a deployment and a bundled site are
configured identically. Unset means no third-party script and no cookies, on
both.

**The `malloyyo` block is a closed schema now.** It used to be an open map where
every key was a publish target — so a mistyped setting silently became a publish
destination, and there was nowhere to put project settings at all. Known keys
are `analytics` and `targets`; targets declared at the top level still work and
print a one-time migration warning; an unrecognised key is dropped and named.

## `useUrlState` — shareable URLs for custom components

A custom component that computes its query inputs in JS had nowhere to put raw,
shareable state. Givens round-trip through the URL as `$NAME`, but a given is
the *governed query contract* — declared in the model, filter-typed, drives the
auto-rendered controls, MCP-visible — and only query-referenced givens are in
`givenSpecs()`, so anything else reached the URL and was never rehydrated. The
component also can't touch the top-level URL itself; it's in a sandboxed
cross-origin iframe.

```jsx
const [rack, setRack] = useUrlState("rack", "");
```

`useState`-shaped, typed by `initial` (string / number / boolean / JSON), stored
under a `~key` param, debounced onto `replaceState`, rehydrated on load. A value
equal to `initial` is dropped so defaults never clutter the link; a malformed
value falls back instead of throwing. `$NAME` and `~key` are separate namespaces
that never collide, and all four hosts carry it — CLI dev (iframe and in-page),
the static bundle, and the hosted app.

## `malloyyo sql`, and an `init` that sets the repo up for agents

- **`malloyyo sql [connection]`** runs raw SQL (from `-e`, `-f`, or stdin)
  against a `malloy-config.json` connection using the bundled DuckDB — so a
  data-site build can read a web URL and `COPY` it into `docs/*.parquet` with
  only `malloyyo` on PATH. It sits below the restricted dashboard runtime on
  purpose; it's a local build/authoring helper.
- **`init` installs two Claude skills** into `.claude/skills/` (idempotent,
  never clobbers): `malloyyo-data-site` (web data URL → Malloy dashboards on
  Pages) and `malloyyo-auto-update` (a weekly GitHub Actions data refresh).
- **`init` also pre-approves the author server's tools** in
  `.claude/settings.json`. It wrote `.mcp.json` but nothing that let those tools
  run without a prompt, so the first compile in a fresh repo stopped for
  approval with no indication why. The rules are derived from `developSurface()`
  rather than hand-listed — the hand-written list is exactly what rotted before
  (it allowed `mcp__malloyyo-local__*` from an older naming scheme, matching
  nothing once the server became `malloyyo_author`).

## The hosted instance, as an image

`docker-publish.yml`: on every merge to main — the same release signal
`cli-publish.yml` uses — the production image is built and pushed to
`ghcr.io/<owner>/malloyyo-server`, tagged `:latest` and `:sha-<sha>` and
reported by immutable digest, which is what hosted deployments pull by. PRs
still only build-and-smoke-test; publishing is release-only, and doc-only
changes are filtered out.

## BIGINTs are numbers again

Malloy's `Result.toJSON()` renders every `numberType: 'bigint'` value as a
decimal string regardless of magnitude, so `1::BIGINT` arrived as `"1"`. Nothing
downstream compensated, and it was entirely silent: lint green, query
successful, chart wrong — a Vega-Lite `quantitative` channel sorts
`"1","10","11","2"` and draws a spoke pattern where a track belongs.

The blast radius is wider than BIGINT: that type covers DuckDB
BIGINT/UBIGINT/HUGEINT/UHUGEINT, every BigQuery INT64, every Snowflake integer
down to tinyint, Postgres/MySQL bigint, and any `sum()` over one of those. On
BigQuery or Snowflake, that's every integer column.

`jsonRows(result)` now backs all four serialization seams (the engine's
`executeMaterialized`, `runMalloy`/`runMalloyFiles`/`runNamedMalloyFiles`, and
the static-site wasm frame). The conversion is **type-driven, not a guess about
what a string looks like** — it reads `result.data.toObject()`, which walks the
same tree with the same normalizers as `toJSON()` and differs in exactly two
ways, and redoes those two conversions itself. A genuine string column holding
`"42"` can never be coerced. Values beyond ±`MAX_SAFE_INTEGER` still serialize
as exact strings; JSON has no int64, and a number that lies is worse than a
string that doesn't — `stable_result` remains the precise channel.

`malloyyo sql` had the same symptom through a different mechanism
(`conn.runSQL()` returns bare rows with no schema, stringified by the driver
before Malloy sees a type). It's routed through Malloy as `<conn>.sql("…")` now,
so its rows carry types too and `--json` matches every other surface. Statements
Malloy can't type — `COPY`, DDL, several at once — fail to *compile*, so nothing
has run, and they fall back to the raw driver exactly as before.

## Failures that name the actual cause

- **A split connection registry no longer blames your config.** A second
  physical copy of `@malloydata/malloy` splits the module-level connection
  registry — the `db-*` packages register with the copy *they* resolve while
  malloyyo reads the copy *it* resolves — and every connection then fails with
  `No connection named "duckdb" found in config`, pointing at a file where
  nothing is wrong. `npx malloyyo` inside a project that already carries
  `@malloydata/*` deps lands here routinely. Now: after registering, we check
  the registry we're about to read is the one that was written to, and an empty
  one throws with every copy of `@malloydata/malloy` reachable from malloyyo and
  from each registry writer — path, version, and who resolves it. Copies are
  compared by **path**, since two directories holding the same version are still
  two registries. A partial split warns once and annotates the eventual error. A
  connector that fails to import is isolated and reported instead of taking the
  other six down with it. (Fixes #136.)
- **Publish failures say what to fix.** An invalid token gets advice keyed to
  where the token came from — `--token`, the config's token env var, or a saved
  login — and a 403 says plainly that the account isn't an admin on that
  instance rather than suggesting a re-login. An unset connection secret is
  named by both ends: the CLI against its own shell (it lints before sending,
  which is where a developer meets the error) and the push route against the
  deployment, adding that secrets don't travel with the model. And a persist
  failure now returns *the model compiled, but saving it failed: `<reason>`*
  instead of dropping the cause.

## Publishing: `--create-dataset`, and a real end-to-end test

Publishing to a dataset that doesn't exist failed with a bare `dataset "x" not
found`. That stays the default — a config typo must not spawn junk datasets —
with `malloyyo publish --create-dataset` as the explicit opt-in. Server-side,
`?create=1` creates the dataset in the **same transaction** as version 1 and
only *after* the model compiles, so a rejected publish still creates nothing.
Created private, owned by the token's user. The ref must be a usable dataset
name (not a uuid), since creating under a slugified variant would leave later
publishes 404ing. A concurrent create gets a 409, not a 500. On an existing
dataset the flag is a no-op, so it's safe to leave in a CI command.

`test/publish-flow.test.ts` boots a test Malloyyo server — the real route
handlers on a `node:http` listener, over a real Postgres — and drives it with
the real CLI binary, covering create + v1, repeat publishes, `status`, and every
case that must create nothing (a model that doesn't compile, a bad name, a bad
token, a non-admin token, `--dry-run`).

**The integration-test harness got safe to run.** It hard-required Docker, wiped
whatever database it was pointed at, and assumed one that starts empty. Now it
autodetects a backend — `YO_TEST_DATABASE_URL` → Docker (the default, and what
CI uses) → a locally installed Postgres in a temp dir, so the suite runs in
agent sandboxes and on macOS runners — it never reads the ambient
`DATABASE_URL`, and it refuses a non-local host or a database with real rows
unless `YO_TEST_FORCE=1`. Each test file gets a fresh schema. `preflight.sh` no
longer hard-fails when Docker is down; it bails only when no backend at all is
available.

## The MCP surface

- **`GET /mcp` answers 405.** Streamable HTTP clients open a GET to listen for
  server→client SSE messages; we send none, so the spec's answer is 405. We
  returned 200 with a plain-text pointer, which the reference client adopts as
  an *open, reconnectable* stream that immediately ends — re-arming with a reset
  attempt counter, so the `maxRetries` cap never trips. One client ran ~1 req/s
  for 11 hours (~30k invocations). Verified against the real SDK client: 7 GETs
  in 8s before, exactly 1 after. The body text stays, since browsers render it
  regardless of status.
- **Every tool result carries `timing`** (`started_at`, `duration_ms`) covering
  the full host round trip — success, validate-only, and error alike — so a
  calling model or a human reading the transcript can see where time went.
- **`userId` on every authenticated request.** Traffic on `/mcp` was only
  attributable when it reached `tools/call`; the reconnect-loop investigation
  above had no user on any log line and had to be correlated against
  `oauth_access_tokens.last_used_at` by hand. POST resolves the token once and
  logs through a child logger carrying requestId + userId + clientId, with a
  line for every JSON-RPC method and a reason on each rejection; GET resolves a
  present bearer purely for attribution. `userId` only, never email or name.

## Docs

- A new `yo_help` topic, **`dashboards/charts`** — there was none on the
  built-in chart tags at all. It leads on the rule that costs the most time: the
  renderer assigns channels by counting **dimensions**, not columns, so a result
  with two dimensions and only `x` named silently promotes the spare one to a
  colour series. It also records that `# hidden` does *not* exempt a dimension
  from that count, and how to sort a named axis (express the sort key as a
  measure — measures are never channels).
- **`dashboards/custom-components`** gains the iframe caveat: a component
  renders on a second origin where the page's CSS variables aren't in scope, so
  styling against `--line`/`--card`/`--muted` leaves every border resolving to
  nothing while text and layout survive.
- The **`malloyyo-data-site` skill** no longer claims each dashboard needs a
  `.jsx`, documents that `dashboard dev` runs queries server-side and holds a
  warm schema cache (model edits hot-reload; a change to the data's *shape*
  needs a restart), and its "done when" now requires *looking at* each rendered
  dashboard — lint compiles without rendering and can't see a chart that throws.
- **The DCO sign-off convention for agent sessions** is written down, and
  deliberately identity-neutral: resolve the signer from the session rather than
  naming anyone in the file, because a hardcoded name makes an agent run by
  another contributor file a false certification the bot can't catch.

- **The package-lock version drift is fixed at the source.** The release job
  bumps `package.json` but stashed npm's lockfile rewrite across the rebase, so
  six releases went by with the lock sitting at 0.2.19. Nothing was broken by it
  — `npm ci` only rejects a lockfile that disagrees on *dependencies* — but
  anyone running `npm install` picked up a version diff they didn't author. The
  release now commits the sync.

## Upgrading from 0.2.19

- **No schema migrations in this batch.** If you're coming from 0.2.7 or
  earlier, [UPGRADING.md](../../UPGRADING.md) still applies in full.
- **If you passed `--analytics`, move it into `malloy-config.json`** under
  `malloyyo.analytics`, or set `ANALYTICS_ID` on a hosted instance. A rebuild
  without it ships no tag.
- **If your `malloyyo` config block holds publish targets at the top level**,
  they still work but now warn — nest them under `targets`. An unrecognised key
  is dropped and named rather than quietly becoming a target.
- **Numbers that used to arrive as strings now arrive as numbers.** If anything
  downstream of a Malloyyo JSON surface was parsing or string-comparing integer
  columns, check it. Values beyond ±`MAX_SAFE_INTEGER` are still strings.
- **If `npx malloyyo` was failing with `No connection named …`,** re-run it —
  the error now tells you whether it's your config or a duplicated
  `@malloydata/malloy` install.
